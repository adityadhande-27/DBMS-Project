What can go wrong?

Suppose both transactions read ₹10,000 before either update is saved.

ATM 1 calculates: ₹10,000 − ₹2,000 = ₹8,000
ATM 2 calculates: ₹10,000 − ₹3,000 = ₹7,000
Lost update risk: If ₹8,000 is written after ₹7,000 without concurrency control, the newer update may be overwritten. The account could show an incorrect balance.

Solution: Timestamp ordering checks whether every read and write follows the required transaction order.

A smaller timestamp means an older transaction. A larger timestamp means a newer transaction. Conflicting operations must respect the serial order T1 → T2.

03

Timestamp Ordering Protocol and Its Rules

The DBMS tracks read and write timestamps for every database item.

Read timestamp

Read_TS(X)

The largest timestamp of any transaction that has successfully read item X.

Example: If T1 and T2 have read Account, Read_TS(Account) = 20.
Write timestamp

Write_TS(X)

The largest timestamp of any transaction that has successfully written item X.

Example: If T2 successfully writes Account, Write_TS(Account) = 20.
↗

Rule 1: Read Operation — Read(X)

If TS(T) < Write_TS(X)

Reject the read and roll back T because a newer transaction has already written X.

Otherwise: Allow the read and update Read_TS(X) to max(Read_TS(X), TS(T)).
↻

Rule 2: Write Operation — Write(X)

If TS(T) < Read_TS(X)

Reject the write: a newer transaction has already read X.

If TS(T) < Write_TS(X)

Reject the write under basic timestamp ordering: a newer transaction has already written X.

Otherwise: Allow the write and set Write_TS(X) = TS(T).

Decision table

OperationConditionDBMS actionReason
Read(X)TS(T) < Write_TS(X)Reject / RollbackA newer transaction already wrote X.
Read(X)TS(T) ≥ Write_TS(X)AcceptRead follows timestamp order.
Write(X)TS(T) < Read_TS(X)Reject / RollbackA newer transaction already read X.
Write(X)TS(T) < Write_TS(X)Reject / RollbackA newer transaction already wrote X.
Write(X)Both checks passAcceptWrite preserves timestamp order.
These rules enforce the serial order established by transaction timestamps. A rejected operation cannot simply proceed as if no conflict occurred.

05

Rollback, Restart, and Database Consistency

Rejecting an operation preserves the required order of conflicting transactions.

What happens to T1?

  • The DBMS aborts or rolls back T1 under basic timestamp ordering.
  • T2 is not automatically rolled back just because T1 fails.
  • If the application retries T1, the restarted transaction receives an appropriate new timestamp.
  • Atomicity ensures an aborted transaction does not leave partial updates visible.

06

Final Analysis, Advantages, and Learning Outcomes

What the ATM case study demonstrates about concurrent transactions.

Advantages

  • Enforces a serial order based on timestamps.
  • Detects operations that violate the required order.
  • Prevents conflicting writes from silently overwriting newer values.
  • Supports consistent concurrent transaction processing.
  • Provides clear rollback conditions.

Limitations

  • Transactions may be aborted and restarted.
  • Repeated conflicts can cause multiple restarts.
  • Timestamp ordering alone does not replace other banking safeguards.

Learning outcomes

  1. Model concurrent ATM transactions.
  2. Assign and compare transaction timestamps.
  3. Trace Read_TS and Write_TS values.
  4. Identify conflicting operations and rollback conditions.
  5. Explain how timestamp ordering preserves database consistency.
Exam-oriented conclusion

Consistency through timestamp ordering

Timestamp-based concurrency control assigns each transaction a logical timestamp and checks every conflicting read and write against the database item's Read_TS and Write_TS. In this example, T2 successfully writes ₹7,000, while T1's later attempt to write ₹8,000 is rejected because TS(T1) < Write_TS(Account). This prevents the older transaction from overwriting the newer accepted update and preserves the required timestamp order.
